## Problem

Settings is the control center for every Birkly install, but today it is the **least polished** admin surface:

| Issue | Impact |
|-------|--------|
| **Monolithic template** | ~2,000 lines inline JS; dead `admin/js/settings.js`; duplicate logic vs standalone pages |
| **Broken feedback** | `showMessage` overridden to `alert()` — saves feel broken |
| **Non-functional tabs** | Storage tab offers DB backends that don't exist; API tab is read-only stub with misleading copy |
| **Save-only security toggles** | Lockout, password rules, CSRF flag persist but may not enforce — trust problem |
| **Wrong data binding** | General → media fields use mismatched keys/units (MB vs bytes, checkbox vs `'on'`) |
| **Subdirectory installs** | Hardcoded `/api/` paths in inline JS (Domains, etc.) |
| **Visual inconsistency** | ~104 inline `style=` attributes; custom tab chrome duplicates `components/tabs.css` |
| **No automated gate** | No `settings_*_test.php`; manual checklist only |

**User goal:** Cleaner, easier settings **without a new design language** — same Birkly tokens, shared components, thoughtful verification that every control actually works.

---

## Vision

Settings becomes a **reference implementation** for Birkly admin UI:

- One tabbed layout using shared `tabs`, `forms`, `cards`, `modals`, `messages` components
- Every control maps **UI → stored value → runtime behavior** with a test
- AI/QA agents run a structured **settings verification matrix** (not ad-hoc clicking)
- Broken or future features are **honest** (hidden, disabled, or labeled “coming soon”) — never fake toggles
- `settings.css` shrinks as rules move to shared components

**Broader admin UI:** In scope only where Settings sets patterns reused elsewhere (toast, tabs, form density). Full admin reskin is out of scope.

## Milestones

### P5.7-M0 — Audit & settings verification matrix

**Goal:** Document every control before changing UI.

**Deliverables:** `docs/reviews/P5.7-settings-audit.md`, `docs/reviews/P5.7-settings-verification-matrix.md`

Each matrix row:

| Column | Purpose |
|--------|---------|
| Tab / section | Where in UI |
| Control label | What user sees |
| JSON / file key | Where value is stored |
| Runtime consumer | PHP/JS that reads it (or **NONE** = save-only bug) |
| Test type | `api` \| `http` \| `manual` \| `defer` |
| Expected behavior | One sentence |
| Current status | pass \| fail \| stub \| untested |

**AI/QA protocol (P5.7-M0-T2):**

1. Agent walks matrix row-by-row — no skipping “boring” toggles  
2. For each control: set value → save → reload → verify persistence → verify runtime effect (or file flag as save-only)  
3. Failed rows become M1–M3 tasks with severity  
4. Stub controls flagged for honest UX (remove or “coming soon”) in M2/M4  

**Acceptance:** Matrix covers 100% of interactive controls across all tabs; human approves scope before M1.

### P5.7-M3 — UI/UX redesign (reuse CSS, minimal new rules)

**Goal:** Cleaner settings using **existing** design system — not a new theme.

**Reuse checklist:**

| Use | From |
|-----|------|
| Tab nav + panes | Align with `admin/css/components/tabs.css` (merge duplicate rules out of `settings.css`) |
| Form fields | `components/forms.css` — `.form-group`, `.input`, `.form-hint` |
| Sections | `components/cards.css` — `.card`, `.card-header` |
| Modals | `components/modals.css` |
| Toggles | `components/switches.css` |
| User/role cards | Existing `.user-card` patterns from `settings.css` or `cards.css` |
| Empty states | `admin/templates/components/empty-state.html` |
| Spacing/type | `core/variables.css` tokens only |

**UX improvements (no new visual language):**

- Consistent section headings + helper text under every group  
- Sticky tab bar on long pages (optional, CSS-only)  
- Primary save actions per tab where logical (not one giant save for everything)  
- Reduce inline `style=` by **≥80%**  
- AI tab: keep working UX; only reorganize markup/CSS scope (`settings-ai` block), don’t rewrite connectors  

**Files:** `admin/css/pages/settings.css` (should **shrink**), `settings.html`, `design-reviewer` sign-off doc

**Acceptance:** Side-by-side with current page — same brand, clearer hierarchy, fewer visual bugs; design-reviewer pass.

## Success criteria

1. Every settings control is in the verification matrix with pass/fail status.  
2. No fake toggles; Storage/API honest.  
3. Settings uses shared tab/form/card/modal/message components; `settings.css` net smaller or scoped.  
4. Toast feedback works; no `alert()` for saves.  
5. Subdirectory installs work for all settings API calls.  
6. Automated test suite guards regressions.  
7. AI/QA matrix executed and documented before closure.
