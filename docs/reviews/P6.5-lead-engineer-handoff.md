## Locked architecture (do not re-ask human)

### Two independent axes

1. **fulfillment** — what happens after payment: `ship` | `deliver` | `register` | `none`
2. **purchase_options[]** — 1..n ways to pay on the SAME sellable unit:
   `{ id, label, billing: one_time|recurring, price_cents, currency, interval? }`

Billing is NOT coupled to fulfillment. Coffee = ship + [one_time AND recurring] on same variant.

### Variants (content model)

- Parent entry = marketing content
- Sub-collection `variants` (convention) = sellable SKUs
- Each variant sub-entry has its own commerce field
- Catalog indexes ONE ROW per sellable unit (variant sub-entry OR parent if no variants)
- Templates buy variant via sub-entry id/slug

No inline variant matrix field. No separate bundle fieldtype in this wave.

### Post-purchase (lean)

PostPurchaseRouter (single class, switch on fulfillment — NO plugin registry in this wave):
- ship → fulfillment adapter + commerce_physical_fulfilled
- deliver → download token + commerce_digital_delivered
- register → EventRegistrationStore + capacity decrement + commerce_event_registered
- none → purchase mappings / automation only + commerce_membership_started when recurring

Idempotent on order_id + line_id. Order lines snapshot commerce value + purchase_option_id at checkout.

### Pattern A for tutorials + community

Two entries (course + membership) — NOT combo purchase_options with includes[] in this wave.

### Backward compatibility

Migrate P6.4 entries: single price_cents + billing → one purchase_option + fulfillment infer:
- default fulfillment `ship` if unknown (document in migration)
- Run migration on plugin bootstrap; tests cover old + new schema

### Platform

- Do NOT build third-party offer-type registry
- Keep shopping_cart + events plugins; payment_shelf alias must still pass tests
