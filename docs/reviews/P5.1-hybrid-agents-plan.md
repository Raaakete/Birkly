# P5.1 — Hybrid AI agents (personal + service)

**Status:** Approved (2026-06-29, Keven)  
**Supersedes:** Flat “one agent = one fixed role” model from P5-M3 without visibility rules  
**Builds on:** P5 complete — per-agent `/mcp/agents/{id}` URLs, OAuth login + consent, role ceiling stopgap

---

## Problem

Phase 5 shipped AI agents with fixed CMS roles and per-agent connector URLs, but:

1. **Privilege escalation risk** — anyone with a service agent URL could connect as that agent’s role (partially mitigated by OAuth consent + rank ceiling; not sufficient for nuanced custom roles).
2. **Wrong mental model** — admins create multiple agents with different roles but users expect “my Claude gets **my** permissions.”
3. **Visibility gap** — all agents visible to every `manage_settings` user; no assignment or role-based listing.
4. **Rank ceiling is coarse** — `admin > editor > viewer` ignores custom roles and granular permissions in `settings/roles.json`.

---

## Approved model: hybrid agents

Two agent **types** only. Same OAuth/MCP transport; different authorization semantics.

### 1. Personal agent (dynamic)

| Property | Value |
|----------|--------|
| **Purpose** | Default connector for each CMS user — “Connect Claude with **my** access.” |
| **Count** | **One per site** (auto-provisioned; not deletable; can be disabled) |
| **Fixed role** | None — effective permissions = **authorizing user’s real CMS role + permission set** at OAuth time |
| **Visibility** | Every user who can access the admin panel |
| **OAuth** | Login + consent; store `authorized_by` + snapshot of user role/permissions on token |
| **Tool execution** | `birkly_ai_user_can_action()` uses authorizer’s permissions, not a stored agent role |
| **URL** | `/mcp/agents/ai_agent_personal_{site}` or stable id `ai_agent_personal` |

### 2. Service agent (fixed)

| Property | Value |
|----------|--------|
| **Purpose** | Shared automation identity — “Claude content bot always acts as **editor**.” |
| **Count** | Zero or more; admin-created |
| **Fixed role** | Admin picks role at create time (unchanged from P5) |
| **Visibility** | **Admin sees all.** Non-admins see only agents where they are **assigned** OR their CMS role is in `visible_to_roles` |
| **OAuth** | Login + consent; only users who **can see** the agent in admin may authorize; deny otherwise |
| **Tool execution** | Fixed agent role; optional cap: effective role = min(agent role, authorizer role) for non-admin authorizers |
| **URL** | `/mcp/agents/{id}` (per agent) |

---

## Visibility matrix

| User | Personal agent | Service agents |
|------|----------------|----------------|
| **Admin** (`*` or `manage_settings`) | See + connect | See all + connect all |
| **Editor** | See + connect (gets editor perms) | Only assigned or `visible_to_roles` includes `editor` |
| **Viewer** | See + connect (gets viewer perms) | Only assigned or `visible_to_roles` includes `viewer` |
| **No admin access** | Hidden | Hidden |

**Assignment fields (service agents only):**

- `visible_to_roles`: string[] — e.g. `["editor"]` means all editors see and may authorize
- `allowed_users`: string[] — explicit user ids (overrides or supplements role visibility; admin always implicit)

---

## Authorization rules (replace rank ceiling)

### Personal agent

```text
can_authorize(user) → user has admin-panel access
effective_permissions → getPermissionsForRole(user.role) + user.permissions[]
```

No agent role field used at tool time.

### Service agent

```text
can_see_in_admin(user, agent) → admin OR role in visible_to_roles OR user in allowed_users
can_authorize(user, agent) → can_see_in_admin AND (admin OR assigned)
effective_role → agent.role (admins) OR min(agent.role, user.role) for non-admin (keep ceiling as safety net)
```

**Deprecate** `birkly_ai_role_rank()` for personal agents; keep only as safety net for service agents until full permission intersection is tested.

## Data model changes

`settings/ai_agents.json` agent record:

```json
{
  "id": "ai_agent_…",
  "type": "personal | service",
  "name": "…",
  "description": "…",
  "role": "editor",
  "visible_to_roles": ["editor"],
  "allowed_users": ["user_abc"],
  "require_approval": true,
  "mcp_endpoint_id": "mcp_ep_…",
  "status": "active",
  "created_by": "…",
  "created_at": "…"
}
```

- `type`: required; default `service` for migrated rows
- `role`: required for `service`; ignored at runtime for `personal` (kept for display/migration)
- Personal agent: `type: "personal"`, singleton enforced in `birkly_ai_agents_ensure_personal()`

---

## Migration

1. On upgrade / first load after P5.1: `birkly_ai_agents_ensure_personal()` creates personal agent if missing.
2. Existing agents → `type: "service"`, `visible_to_roles: ["admin"]` only (admin-only until admin re-assigns).
3. Admin UI banner: “Service agents are now admin-only by default. Assign roles or users to share.”

## Admin UX

### Settings → AI → Connect your AI app

**Section A — Personal agent (top, highlighted)**

- Card: “Your personal connector” — one URL, copy button
- Copy: “Connect Claude with **your** Birkly permissions. Each team member uses the same URL but signs in with their own account.”

**Section B — Service agents**

- List filtered by visibility for current user
- Create modal: type = Service (Personal not in create — auto exists)
- Fields: name, description, **role**, **Who can use this agent** (multi-select roles + specific users), require approval
- Admin-only: edit visibility

---

## OAuth / MCP flow (unchanged transport)

1. Claude → per-agent URL
2. Birkly login if needed
3. Consent screen shows agent **type**, name, and effective access summary:
   - Personal: “You will connect as **{user role}** with your current permissions.”
   - Service: “You will connect as **{agent name}** with **{agent role}** access.”
4. Token stores `authorized_by`, `agent_type`, and for personal: `authorized_permissions` snapshot or live resolve from user id
